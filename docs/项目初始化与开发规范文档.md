# 项目初始化与开发规范文档

## 1. 文档目的

本文档用于指导工程初始化和后续开发协作。目标是在 MVP 阶段保持项目结构清晰、战斗模拟可测试、词条内容可维护、渲染和 UI 不污染核心逻辑。

## 2. 技术栈确认

MVP 技术栈：

- 语言：TypeScript
- 工作区：pnpm workspace
- 前端：Vite + React
- 渲染：PixiJS
- 战斗模拟：纯 TypeScript
- 单元测试：Vitest
- 浏览器冒烟测试：Playwright

后续预留：

- 服务端：Node.js + Fastify
- 数据库：PostgreSQL
- 实时通信：WebSocket

## 4. 包职责

### apps/web

负责浏览器应用。

包含：

- 配置界面
- 词条选择 UI
- 预设敌人选择
- PixiJS 渲染入口
- 战斗 HUD
- 结算界面
- 本地存储

不得包含：

- 核心战斗规则
- 词条结算逻辑
- 伤害/状态/召唤规则

### packages/sim

负责纯战斗模拟。

包含：

- 固定步长模拟
- RNG
- 小球移动
- 碰撞
- 伤害
- 状态
- 子弹
- 召唤
- 词条行为
- 胜负结算

不得依赖：

- React
- PixiJS
- DOM
- Canvas
- 浏览器真实时间

### packages/content

负责静态内容。

包含：

- 30 个 MVP 词条定义
- 6 个预设敌人
- 基础数值配置
- 平衡常量

不得包含：

- 与渲染绑定的代码
- 不可序列化的运行时状态

### packages/shared

负责共享类型和校验。

包含：

- BuildConfig
- MatchConfig
- TraitDefinition 相关类型
- 版本号
- schema 校验

不得包含：

- 具体战斗行为
- UI 组件
- PixiJS 代码

### tools

负责开发辅助工具。

包含：

- 批量模拟
- 平衡报告
- 词条合法性检查

## 6. 命名规范

### 文件命名

- TypeScript 文件使用 kebab-case。
- React 组件文件可使用 PascalCase。
- 词条数据文件按类型拆分。

示例：

```txt
collision-system.ts
damage-system.ts
TraitCard.tsx
attribute-traits.ts
collision-traits.ts
```

### ID 命名

词条 ID 使用 snake_case。

示例：

```txt
hp_boost
speed_boost
collision_lifesteal
projectile_bounce
death_split
```

实体 ID 由模拟器生成，不使用展示名。

### 类型命名

TypeScript 类型使用 PascalCase。

示例：

```ts
type BuildConfig = {};
type MatchConfig = {};
type TraitDefinition = {};
```

## 7. 代码边界

### 模拟层边界

模拟层允许：

- number/string/boolean/object/array
- 自定义 Vec2
- seed RNG
- 纯函数和可测试类

模拟层禁止：

- `Math.random()`
- `Date.now()`
- `performance.now()`
- `window`
- `document`
- React hook
- PixiJS 对象

### 渲染层边界

渲染层允许：

- PixiJS
- 读取 WorldSnapshot
- 播放 BattleEvent 对应特效

渲染层禁止：

- 修改 BattleWorldState
- 重新计算伤害
- 私自决定胜负

### UI 层边界

UI 层允许：

- 生成 BuildConfig
- 生成 MatchConfig
- 启动/暂停/重开战斗
- 展示快照和结算

UI 层禁止：

- 直接修改小球生命
- 直接生成子弹
- 直接触发词条效果

## 8. 新增词条流程

新增一个词条时按以下步骤：

1. 在 `packages/content` 中新增 TraitDefinition。
2. 确认 ID、展示名、功能副标题、主类型、多标签。
3. 定义重复规则。
4. 定义数值配置。
5. 如果是静态属性词条，只补充 statModifiers。
6. 如果是运行时行为词条，在 `packages/sim` 中实现 behavior。
7. 将 behaviorKey 与实现注册到词条行为表。
8. 增加单元测试。
9. 在 UI 中确认展示正常。
10. 用至少一个手动对局验证可观察。

## 9. 词条数值修改流程

修改词条数值时：

- 优先修改 `packages/content` 的数值配置。
- 不直接修改 sim 规则代码，除非机制本身变化。
- 修改后运行相关单元测试。
- 对重点构筑运行批量模拟。
- 在文档中记录明显口径变化。

## 10. 测试规范

### 必须测试的内容

- BuildConfig 校验。
- MatchConfig 校验。
- 基础碰撞伤害。
- 碰撞冷却。
- 吸血上限。
- 反伤不连锁。
- 召唤物数量上限。
- 死亡分裂判负。
- 复活一次。
- 状态刷新不叠层。
- 弹道分裂不递归。

### 测试放置建议

```txt
packages/sim/src/**/*.test.ts
packages/shared/src/**/*.test.ts
packages/content/src/**/*.test.ts
apps/web/tests/**/*.spec.ts
```

## 11. 提交前检查

每次较大改动前建议运行：

```txt
pnpm typecheck
pnpm test
pnpm build
```

涉及 UI 流程时运行：

```txt
pnpm test:e2e
```

MVP 初期如果 e2e 尚未建立，至少手动验证：

- 页面能打开。
- 能选满 4 个词条。
- 能开始战斗。
- 能出现结算。

## 12. 文档维护规范

当以下内容变化时，需要同步更新文档：

- 技术栈变化。
- 目录结构变化。
- 词条数量或机制变化。
- 基础数值变化。
- 战斗结算规则变化。
- 构筑数据结构变化。
- 联机/后端阶段提前或推迟。

优先更新文档：

- PRD：产品口径变化。
- 技术栈与架构设计：技术路线变化。
- 数据模型设计：类型与配置变化。
- 战斗模拟系统设计：规则执行顺序变化。
- MVP 功能清单：功能范围变化。
- 实施计划：开发阶段变化。

## 13. 初始开发顺序

工程初始化后建议按以下顺序开始：

1. 建立 workspace。
2. 建立 shared 类型。
3. 建立 content 中的基础数值和词条数据。
4. 建立 sim 的 fixed tick battle。
5. 跑通无词条对战。
6. 接入 PixiJS 渲染。
7. 做最小配置界面。
8. 开始逐类实现词条。

## 14. 暂不引入的内容

MVP 初期暂不引入：

- 后端服务。
- 数据库。
- 登录系统。
- 复杂 UI 组件库。
- 地图编辑器。
- 词条编辑器。
- 实时联机。
- 录像系统。

这些内容后续按阶段设计，不在初始化阶段增加工程复杂度。
