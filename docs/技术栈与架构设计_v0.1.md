# 技术栈与架构设计 v0.1

## 1. 结论

项目采用 **TypeScript Web 技术栈**，核心原则是：

- 战斗模拟与渲染/UI 解耦。
- MVP 先做纯前端单机 Demo。
- 战斗核心保持确定性，后续可复用于擂台战、录像回放、自动平衡测试和服务端校验。
- 后端与实时联机后置，但从数据结构和目录架构上提前预留。

推荐技术栈：

- 语言：TypeScript
- 包管理与工作区：pnpm workspace
- 前端构建：Vite
- UI 框架：React
- 战斗渲染：PixiJS
- 样式：CSS Modules / 普通 CSS，MVP 暂不引入重型 UI 组件库
- 战斗模拟：纯 TypeScript 自研固定步长模拟器
- 配置校验：Zod 或等价 schema 校验库
- 单元测试：Vitest
- 端到端/视觉冒烟测试：Playwright
- MVP 存储：localStorage / IndexedDB，本地 JSON 导入导出后续加入
- 后续服务端：Node.js + Fastify + PostgreSQL
- 后续实时房间：WebSocket，自动战斗阶段优先同步构筑与随机种子，而不是逐帧同步输入

## 2. 选择理由

### 为什么选 Web + TypeScript

本项目的核心是“构筑配置 + 自动战斗 + 可分享对局”。Web 技术栈天然适合快速分发、浏览器试玩、后续上传构筑和分享挑战链接。

TypeScript 可以让词条、构筑、战斗事件、实体状态拥有明确类型。更重要的是，战斗模拟核心可以同时运行在浏览器和 Node.js 服务端，后续用于擂台战校验、批量自动对战、平衡测试和好友对战结果复现。

### 为什么选 PixiJS，而不是直接使用完整游戏引擎

PixiJS 负责高性能 2D 渲染即可。我们的碰撞、词条、状态、召唤、胜负都要由自研模拟器控制，不能被渲染引擎或物理引擎绑死。

这样可以保证：

- 战斗逻辑可测试。
- 战斗结果可复现。
- 后续服务端可以不依赖 Canvas/WebGL。
- 词条系统不会和渲染框架耦合。

### 为什么不用 Pygame 作为主路线

Pygame 适合快速本地原型，但不适合作为后续擂台战、好友对战、网页分享和跨设备试玩的主路线。它仍可作为参考项目，但不建议作为本项目主工程基础。

### 为什么暂不选 Unity/Godot

Unity/Godot 都能完成这个游戏，但当前需求的 MVP 重点是机制验证、词条构筑、自动模拟和后续 Web/服务端复用。使用完整引擎会增加工程体量和联机/数据复用成本。若后续明确要做移动端原生发行，再重新评估引擎路线。

## 4. 核心架构

### 分层结构

```txt
React UI
  负责配置界面、词条选择、预设敌人选择、结算界面

PixiJS Render
  负责画小球、子弹、召唤物、特效、数字、场地

Battle Simulator
  纯 TypeScript 战斗模拟，固定步长运行，不依赖 DOM/Pixi/React

Content Data
  词条定义、预设敌人、基础数值、平衡配置

Storage
  本地构筑保存、导入导出、后续擂台战上传
```

### 数据流

```txt
玩家选择词条
  -> 生成 BuildConfig
  -> 生成 MatchConfig：蓝方构筑、红方构筑、随机种子、版本号
  -> Battle Simulator 编译构筑并初始化战斗
  -> 每 tick 输出 WorldSnapshot + BattleEvents
  -> PixiJS 根据 Snapshot 绘制
  -> React 展示 UI 状态和结算
```

## 5. 战斗模拟设计

### 固定步长

战斗模拟使用固定步长，例如：

```txt
tickRate: 60
dt: 1 / 60
```

渲染帧率可以与模拟帧率不同。渲染层只消费最新快照，不直接改变战斗状态。

### 确定性原则

MVP 起就要保证以下约束：

- 所有随机数来自可传入 seed 的 RNG。
- 模拟层不读取系统时间。
- 模拟层不读取 DOM、Canvas、鼠标、键盘。
- 模拟层不使用 PixiJS 对象。
- 相同构筑、相同版本、相同 seed 应产生相同结果。

这对后续擂台战、录像回放、自动平衡测试非常重要。

### 实体模型

MVP 实体类型：

- Ball：主球、分身、分裂体。
- Projectile：普通子弹、小子弹。
- Turret：自动炮台。
- StatusEffect：燃烧、中毒、减速、脆弱、护盾。
- BattleEvent：伤害、治疗、死亡、爆炸、状态附加、特效提示。

后续可扩展：

- Zone：毒区、加速区、减速区、陷阱。
- Beam：激光。
- Missile：导弹。
- OrbitObject：轨道物。

## 6. 词条系统架构

### 词条结构

词条采用“机制 ID 与展示名称分离”的结构。展示名后续可以改，机制 ID 不轻易改。

```ts
type TraitDefinition = {
  id: string;
  name: string;
  subtitle: string;
  mainType: TraitType;
  tags: TraitTag[];
  repeatRule: RepeatRule;
  description: string;
  statModifiers?: StatModifier[];
  behaviorKeys?: string[];
};
```

### 词条执行模型

词条分为两类能力：

- 静态修正：生命、速度、半径、碰撞伤害、减伤等。
- 运行时行为：碰撞吸血、撞墙蓄力、生成分身、子弹分裂、低血狂暴等。

推荐生命周期钩子：

```txt
onBuildCompile
onBattleStart
onTick
onWallBounce
onCollision
onProjectileFire
onProjectileHit
onDamage
onHeal
onDeath
onKill
onBattleEnd
```

MVP 不需要实现全部钩子，但架构上按事件驱动设计，避免把 30 个词条写成互相缠绕的特判。

## 7. 构筑与对战数据

### 构筑配置

构筑配置只描述一个小球。

```ts
type BuildConfig = {
  version: string;
  name: string;
  skin: string;
  baseModel: string;
  traits: string[];
};
```

MVP 约束：

- `traits.length === 4`
- 词条 ID 必须存在于当前词条库
- 重复词条必须符合该词条的 repeatRule

### 对战配置

对战配置描述一次战斗。

```ts
type MatchConfig = {
  version: string;
  seed: number;
  blue: BuildConfig;
  red: BuildConfig;
  arenaId: string;
};
```

后续擂台战上传的是 BuildConfig；录像/复现需要 MatchConfig。

## 8. 前端界面架构

MVP 页面流程：

```txt
配置界面
  -> 开始战斗
  -> 结算界面
  -> 返回配置
```

React 负责：

- 词条列表与筛选
- 蓝方/红方构筑配置
- 预设敌人选择
- 开始战斗按钮
- 战斗 HUD
- 结算面板

PixiJS 负责：

- 场地
- 小球
- 子弹
- 召唤物
- 伤害数字
- 状态/爆炸/护盾/吸血等视觉反馈

React 不直接修改战斗世界；只通过 MatchConfig 初始化战斗。

## 9. 后续在线架构

### 擂台战

阶段 1 可以只上传构筑：

```txt
玩家上传 BuildConfig
其他玩家下载构筑
本地生成 MatchConfig 并挑战
```

阶段 2 再加入服务端校验：

```txt
服务端运行同一套 sim
记录结果、战斗时长、关键统计
防止客户端伪造胜负
```

### 好友对战

由于战斗中没有玩家操作，实时好友对战不需要复杂逐帧输入同步。

推荐流程：

```txt
玩家 A 创建房间
玩家 B 加入房间
双方提交 BuildConfig
服务端生成 seed
双方用同一个 MatchConfig 本地模拟
服务端可选择同步结果或做权威校验
```

如果后续加入战斗中手动操作，再重新设计实时同步方案。

## 10. 测试与平衡工具

### 单元测试

使用 Vitest 测试：

- 基础伤害结算。
- 碰撞冷却。
- 词条重复规则。
- 吸血上限。
- 召唤物上限。
- 复活/死亡分裂。
- 子弹弹射、穿透、分裂。

### 批量模拟

需要提供命令行工具批量运行对战：

```txt
构筑 A vs 构筑 B，运行 100 局
输出胜率、平均时长、平均剩余生命、平均伤害、异常局
```

这会成为后续平衡核心工具。

### 浏览器冒烟测试

使用 Playwright 做最小冒烟测试：

- 页面能打开。
- 能选择 4 个词条。
- 能开始战斗。
- 战斗画面非空。
- 结算能出现。

## 11. MVP 实施顺序

推荐按以下顺序开发：

1. 搭建 TypeScript + Vite + React + PixiJS 项目。
2. 建立 sim 核心：固定步长、RNG、Ball、Arena、碰撞、胜负。
3. 建立基础渲染：场地、小球、生命数字、碰撞反馈。
4. 建立 BuildConfig 和 MatchConfig。
5. 实现属性类与碰撞类词条。
6. 实现弹道类词条。
7. 实现召唤类、状态类、规则类词条。
8. 实现配置界面、预设敌人、结算界面。
9. 加入 Vitest 基础测试和批量模拟工具。
10. 进行第一轮数值平衡。
